AIS-Edge · tier-2 · management and edge

Two machines between your scanners and XNAT

Tier-2 has an edge machine in the hospital and a management machine in a central place. The edge receives studies, keeps the originals and removes the patient identity. accessionflow
The pipeline tool. It collates, labels, de-identifies and stores each study. It was called xnat-ingest before.

accessionflow's names for three stages: gather a study into one folder, write its XNAT labels, send it to XNAT. Pod names, log commands and settings still use the older names group, assign and upload. This page shows the names that work.

accessionflow's word for one study on its way through the pipeline. XNAT calls it a session. One series in it is an acquisition, and XNAT calls that a scan.

The rules for what is kept on each machine and for how long. It is off on a new install.

Four facts that surprise people

Fact 1

The XNAT labels are written before de-identification

The label stage reads three tags and writes the labels. De-identify runs after it. The recipe cleans the files, but it cannot change the labels.

Example values only. Not a real patient.

What to do: agree the subject and session tags with the privacy owner before setup. If the scanner writes a study code for each person, use that tag for the subject. Chapter 4, question 3, helps you choose.

Fact 2

The AE title does not choose the project

Orthanc accepts a study from any device that can reach port 4242 of the edge, under any AE title. The tags choose the project, not the AE title.

any device on the LAN→:4242→Orthanc→tags pick the project→XNAT

So the firewall rule on port 4242 is the real lock.

Allow only the scanners and the PACS to reach port 4242 of the edge. Any other device that reaches the port can send studies too.

Fact 3

The edge holds no XNAT password

The edge can do one thing outside the hospital: write to its own bucket on the management machine. It has a key and a certificate for that, and nothing else. Only the management machine talks to XNAT.

edge→:443→its own bucket→store stage→XNAT

The edge always opens the connection, outbound, to port 443 of the management machine. After the one-time join, nothing connects into the hospital except the scanners on port 4242.

Fact 4

Nothing is cleaned up until you turn the data policy on

On a new install the data policy is off. Studies still flow, but the copy in Orthanc, the clean copy on the edge and the staged copy on the management machine all stay, so the disks fill. You run the policy in dry run for a week, read what it would remove, and then turn it on.

Your site decides the labels and the recipe

Each edge chooses which tags make the XNAT labels, and which tags the recipe removes. Chapter 4 helps you choose both, and writes the result into the site files.

Question 4 · the recipe

Which tags the recipe removes

The recipe is a list with one line for each tag. REMOVE PatientName removes that tag from every file. A tag that is not in the list goes to XNAT unchanged. The key is ingest.deidentify.specs. This is the shipped recipe: click Keep, Remove or Shift on a tag.

    • Private tags, the vendor blocks such as (0019,xxxx), pass through. So do sex, age and the study date, unless you change them here. Decide this with the privacy owner.
    • The removed values are not lost. The de-identify stage writes them to a map in /data/xnat-ingest/reid, so a study can be traced back. Keep the switch below on, and the install makes the key that encrypts that map.
    • A project recipe replaces the default recipe for that project, so it must name every tag. Keep the __default__ recipe for all other projects.

    Not encrypted: the map is then a plain file on the disk. Anyone who can read the disk can read the removed names and numbers.

          Chapter 6

          When something breaks

          Pick what you see. Each answer says the cause, the fix, and the alert that tells you. Unless it says otherwise, a command runs on the management machine, from the ais-edge folder.

            The install stops and names policyReviewed

            Cause
            The privacy approval is not recorded in the edge file. It stops at part 7, after the edge has joined.
            Fix
            Get the approval for the label tags and the recipe. Then do install step 7, and run ./install.sh demo-mgmt again. Answer s to the parts that are done.

            The install stops and names emailTo or smtpHost

            Cause
            The management file has no alert recipient or no mail server. The install refuses, because alerts would then go nowhere.
            Fix
            Answer question 6 in chapter 4, do install step 5 again, and run the install again.

            The install says the secrets have placeholders, or do not match the site file

            Cause
            A REPLACE_ value or an example.org value is still in the management secrets, or the edge name in the site file has no upload key. The message names the line.
            Fix
            Run scripts/site-secrets.sh edit demo-mgmt, correct the value, save, and run the install again. If you changed the edge name after step 4, start step 4 again in a fresh copy of the repository.

            The install fails with "conversion webhook ... connection refused"

            Cause
            Part 2 of the install was skipped, or its programs are not ready yet. The management chart needs them first.
            Fix
            Run the install again and answer y to part 2. Do not set certManager.enabled to true: the file keeps it false on purpose.

            The edge does not join

            Cause
            The management machine cannot log in to the edge, the edge cannot reach port 443 of the management machine, or a bundle was run after its two hours.
            Fix
            From the edge, curl -kI https://10.0.0.1 must print an HTTP line. A 404 is fine: it shows that the path is open. For the SSH join, repeat the three commands of install step 3. Then run the install again: it picks up where it stopped, and makes a fresh bundle if you use one.

            Edge pods show CreateContainerConfigError

            Cause
            A Secret is missing on the edge. Most often it is one of the four that the management machine delivers: the certificate authority, the log certificate, the upload key or the upload certificate.
            Fix
            Deliver them again now, and read what the delivery says:

kubectl -n ais-mgmt logs job/cert-sync-now --tail=30
            Afterwards remove the job with kubectl -n ais-mgmt delete job cert-sync-now.

            Fix

            IngestStageError

            The edge cannot send to the staging store

            Cause
            The edge cannot reach the management machine, or its upload key or certificate is missing or out of date.
            Fix
            The edge keeps its copy and tries again, so nothing is lost. Read kubectl --kubeconfig kubeconfig-demo-edge -n xnat-ingest logs -l component=s3-uploader --tail=50. For a key or certificate error, deliver the Secrets again (see "Edge pods show CreateContainerConfigError").
            Alert
            S3UploaderRetryStorm

            XNAT rejects the login

            Cause
            The XNAT user or password is wrong, or the account was locked or changed. Studies wait in the staging store meanwhile.
            Fix
            Correct xnat-credentials, apply, and restart the store stage: 
            scripts/site-secrets.sh edit demo-mgmt
scripts/site-secrets.sh apply demo-mgmt
kubectl -n xnat-upload rollout restart deploy/mgmt-upload-demo-edge
            apply asks before it writes: answer y. Run it with the default kubectl, as here, so that it writes to the management machine.
            Alert
            XNATAuthFailure

            XNAT already has the session, with different files

            Cause
            The store stage found files in XNAT that do not match its own, and it will not change a scan that XNAT already holds. One way to get here: the rest of a series arrives after the clean-up removed the first part.
            Fix
            The staged copy stays, and nothing is lost. Compare the session in XNAT with the staged files. Do not delete either side before you know which is complete, and ask the maintainers if you are not sure.
            Alert
            XNATResourceIncompleteAndStuck

            A disk is filling

            Cause
            With the data policy off or in dry run, nothing is removed, on the edge or in the staging store.
            Fix
            Add disk space now. Then turn on the data policy, one week in dry run first (install step 12). Never delete from the pipeline folders or the staging store by hand.
            Alert
            EdgeDiskLow SeaweedFSDiskFull

            Nothing arrives at all

            Cause
            The firewall blocks port 4242 of the edge, or the scanner has the wrong IP address, port or AE title.
            Fix
            Check the scanner: AISEDGE, 10.0.0.2, port 4242. Watch kubectl --kubeconfig kubeconfig-demo-edge -n xnat-ingest logs -l component=dicom-receiver --tail=20 -f while it sends.

            No alert mail arrives

            Cause
            The mail server refuses the login, or the address or server in the management file is wrong.
            Fix
            Send the test alert from install step 11 and read what Alertmanager says: kubectl -n ais-mgmt logs alertmanager-mgmt-kube-prometheus-stack-alertmanager-0 -c alertmanager --tail=50. Correct the mail answers in chapter 4, or the mail password with scripts/site-secrets.sh edit demo-mgmt.

            Nine rules

            1. Do not lose the age key.There is no recovery. Without it, nobody can decrypt the secrets.
            2. Do not change the label tags after the first upload.The same patient then gets a second subject in XNAT, and nothing warns you.
            3. Do not delete a study from Orthanc to fix it.Follow docs/components/accessionflow.md.
            4. Do not delete from the pipeline folders or the staging store by hand.A folder that looks left over can be the only copy of a study.
            5. Do not copy the data policy into an edge file.It is written once, in the management file. A second copy on an edge makes the two clean-ups disagree.
            6. Do not turn off the facility backup.It is the only copy of the originals.
            7. Copy the backup before scripts/uninstall.sh.That script deletes the data on both machines, the facility backup too.
            8. Keep patient data off tickets and chat.ais-requeue show and the stage logs can print it.
            9. Run verify-live after every change.After an upgrade, a secret change, or a reboot of either machine.

            Chapter 7

            Practise before the real install

            Do the install once on two test machines with a test XNAT project, and break it on purpose. Then the real install holds no surprises.

            1. Stage 1 · 30 minThe picture

              Play the study in chapter 1 twice: once with the technical words, once with the mail-room words. Then switch on quiz mode in chapter 2.

              Done when you can tell the path of one study, and say which machine does what.

            2. Stage 2 · a few daysThe facts

              Collect chapter 3 from the people who own each fact. Answer chapter 4 with the scanner team and the privacy owner.

              Done when chapter 4 says the files are ready to copy.

            3. Stage 3 · half a dayA practice install

              On two test machines, with a test XNAT project and a phantom study. Follow chapter 5, then do the four drills below.

              Done when you fixed every drill without help.

            4. Stage 4 · a dayThe real install

              The same steps on the real machines, with the real answers.

              Done when verify-live shows no failures and one test study is in XNAT.

            Four drills for stage 3

            1. An empty tag

            From the PC, send a copy of the test study with an empty AccessionNumber. The second line gives the copy a new study number, so that it is a new study and not more images for the first one.

            mkdir drill && cp study/*.dcm drill/
U=2.25.$(date +%s%N)
dcmodify -nb -gin -m "(0020,000d)=$U" -m "(0020,000e)=$U.1" -m "(0008,0050)=" drill/*.dcm
storescu -aec AISEDGE -aet TEST_MOD 10.0.0.2 4242 drill/*.dcm

            You should see: after about two minutes, sudo ais-requeue list on the edge machine shows the study, and InvalidSessionAssigned fires. Fix it: sudo ais-requeue requeue <folder> --session DRILL$(date +%d%H%M), also on the edge. The session then appears in XNAT under that label. The date in the label keeps it different each time: XNAT accepts a session label only once in a project.

            2. A wrong password

            Put a wrong XNAT password in with scripts/site-secrets.sh edit demo-mgmt, then apply it and restart the store stage (chapter 6, "XNAT rejects the login").

            You should see: scripts/verify-live.sh demo-mgmt fails on the XNAT login, and a new test study waits in the staging store. Fix it: the same three commands with the right password. Do this drill with a test account only, and fix it within a few minutes: many wrong logins can lock an XNAT account. The waiting study then goes to XNAT by itself.

            3. The edge goes away

            Restart the edge machine with sudo reboot.

            You should see: the edge comes back by itself within a few minutes, and verify-live shows 0 failed. If it stays away for more than 5 minutes, EdgeWorkerDisconnected fires, and it clears when the edge is back.

            4. A dry run of the data policy

            Choose Dry run in chapter 4, question 5. Do install step 5 again and run the install again.

            You should see: the install ends with "DRY RUN". After the test study is older than your waiting times, the three logs of install step 12 name it. Nothing is removed.
