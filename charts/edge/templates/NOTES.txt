{{- if eq .Values.dataPolicy.derived.grouped.reclaim "never" }}

  NOTE: grouped.reclaim = never. `assign --loop` rebuilds its work list from
  a live listing of /data/grouped every cycle, so the same sessions will be
  re-assigned indefinitely — /data/assigned is repopulated, the uploader
  re-stages, and the upload-success alert re-fires. /data/grouped holds
  hardlinks, and the bytes also live in Orthanc storage and the facility
  backup, so onAssigned deletes no data. Prefer onAssigned unless you have a
  specific reason.

CHECK IT IS WORKING

  FIRST, and after every upgrade:
    scripts/verify-live.sh <site>

  Helm having accepted these objects does not mean the pipeline runs. That
  script checks readiness rather than pod phase, reaches XNAT from inside the
  upload pod with the site's own credentials, and confirms the alert rules
  actually loaded. Its exit code is the number of failures.

  It cannot see DICOM port {{ .Values.orthanc.dicomPort }} — that is a hostPort,
  invisible from inside the cluster — so it reports that one as SKIP. Prove it
  with a real C-STORE, below.

  By hand:
    kubectl -n {{ .Values.namespace }} get pods
  kubectl -n {{ .Values.namespace }} logs -l component=group     -f
  kubectl -n {{ .Values.namespace }} logs -l component=assign    -f
{{- if eq .Values.upload.mode "s3" }}
  kubectl -n {{ .Values.namespace }} logs -l component=s3-uploader -f
{{- else }}
  kubectl -n {{ .Values.namespace }} logs -l component=upload    -f
{{- end }}

  Send a test study:
    dcmsend <node-ip> {{ .Values.orthanc.dicomPort }} -aec {{ .Values.orthanc.aet }} /path/to/study/

NOT REMOVED BY `helm uninstall`
  The namespace, both PersistentVolumes and both PersistentVolumeClaims carry
  helm.sh/resource-policy: keep and Retain. Uninstalling this release leaves
  every received study, and the Secrets above, in place. Removing data is a
  separate deliberate act.
