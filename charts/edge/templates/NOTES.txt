DATA POLICY  {{ if .Values.dataPolicy.enabled }}{{ if .Values.dataPolicy.dryRun }}DRY RUN{{ else }}ENFORCING{{ end }}{{ else }}NOT ENFORCED{{ end }}
{{- if not .Values.dataPolicy.enabled }}
  dataPolicy.enabled is false, so nothing expires and nothing is reclaimed.
  Disk will grow without bound. Set it once you have decided the retention
  rules for this site.
{{- else if .Values.dataPolicy.dryRun }}
  dryRun is true: reclaim decisions are logged but not acted on. Watch a few
  days of logs, confirm they match your expectations, then set dryRun: false.
{{- end }}
{{- if eq .Values.dataPolicy.derived.grouped.reclaim "onAssigned" }}
  dataPolicy.enabled and dryRun govern the data policy and the reclaimers
  only. assign still removes /data/grouped/<session> after it writes the
  session to /data/assigned, because grouped is onAssigned. That moves data
  along the pipeline. It does not remove the last copy.
{{- end }}
{{- if not .Values.storage.facilityBackup.enabled }}

  ⚠  FACILITY BACKUP IS OFF
    No original is kept outside the pipeline, so Orthanc and the pipeline
    folders hold the only copy of each study.
{{- if eq .Values.dataPolicy.derived.orthancStorage.reclaim "onGrouped" }}
    derived.orthancStorage.reclaim is onGrouped, so an armed data policy
    deletes the Orthanc copy of a staged study after its minAge. A session in
    assigned/__invalid__/ is then the only copy.
{{- end }}
    Turn the backup on unless the site keeps its originals somewhere else.
{{- end }}

{{- if eq .Values.dataPolicy.derived.grouped.reclaim "never" }}

  NOTE: grouped.reclaim = never. `assign --loop` rebuilds its work list from
  a live listing of /data/grouped every cycle, so the same sessions will be
  re-assigned indefinitely — /data/assigned is repopulated, the uploader
  re-stages, and the upload-success alert re-fires. /data/grouped holds
  hardlinks, and the bytes also live in Orthanc storage and the facility
  backup, so onAssigned deletes no data. Prefer onAssigned unless you have a
  specific reason.

CHECK IT IS WORKING

  FIRST, and after every upgrade:
    scripts/verify-live.sh <site>

  Helm having accepted these objects does not mean the pipeline runs. That
  script checks readiness rather than pod phase, reaches XNAT from inside the
  upload pod with the site's own credentials, and confirms the alert rules
  actually loaded. Its exit code is the number of failures.

  It cannot see DICOM port {{ .Values.orthanc.dicomPort }} — that is a hostPort,
  invisible from inside the cluster — so it reports that one as SKIP. Prove it
  with a real C-STORE, below.

  By hand:
    kubectl -n {{ .Values.namespace }} get pods
  kubectl -n {{ .Values.namespace }} logs -l component=group     -f
  kubectl -n {{ .Values.namespace }} logs -l component=assign    -f
  kubectl -n {{ .Values.namespace }} logs -l component=upload    -f

  Send a test study:
    dcmsend <node-ip> {{ .Values.orthanc.dicomPort }} -aec {{ .Values.orthanc.aet }} /path/to/study/

NOT REMOVED BY `helm uninstall`
  The namespace, the PersistentVolumes and their claims carry
  helm.sh/resource-policy: keep and Retain. Uninstalling this release leaves
  every received study, and the Secrets above, in place. Removing data is a
  separate deliberate act.
{{- if .Values.storage.storageClass.create }}
  The cluster-scoped StorageClass {{ .Values.storage.storageClass.name }} is kept too. A release
  with another name cannot take it over: set storage.storageClass.create: false,
  or delete it (kubectl delete storageclass {{ .Values.storage.storageClass.name }})
  when no PersistentVolume uses it.
{{- end }}

  ⚠  NO ALERT CAN BE DELIVERED FROM THIS SITE

    Filling in the alertmanager-smtp Secret is NOT enough on its own. That is

          alerting:
            emailTo: imaging-ops@example.org
            emailFrom: ""          # defaults to emailTo
            smtpHost: smtp.example.org
            smtpUsername: ""       # must match `username` in alertmanager-smtp

    If this site is deliberately without email, ignore this: nothing else
    depends on it.
